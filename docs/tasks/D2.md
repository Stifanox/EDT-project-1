**Właściciel:** O1 · **Zależności:** !P0 · **Status:** patrz [`PROGRESS.md`](../../PROGRESS.md)

## Cel
Trwałe przechowywanie celów, opinii i predykcji, żeby dane przetrwały restart, a CLI (D5) mogło pisać do tej samej bazy co GUI.

## Zakres
- `SqliteReviewRepository` implementujący `ReviewRepository`.
- Schemat: `targets`, `reviews`, `predictions` (+ indeksy), migracja przez `CREATE TABLE IF NOT EXISTS`.
- Bezpieczny dostęp z wielu wątków Streamlit i z drugiego procesu (WAL).

## Kontrakt / API
Udostępnia `ReviewRepository`. Ścieżka bazy: `config.DB_PATH`, czytana w chwili wywołania fabryki.

## Kryteria akceptacji
- [x] `SqliteReviewRepository` przechodzi test kontraktowy (dopisany do `REPOSITORY_FACTORIES`)
- [x] Schemat: `targets`, `reviews`, `predictions` z kluczami głównymi i indeksami po (`target_id`, `created_at`) i `model_name`
- [x] Daty zapisywane w UTC, odczytywane jako aware; `extra` jako JSON; `label` jako NULL / tekst
- [x] `config.DB_PATH` czytany w chwili wywołania; brakujący katalog tworzony automatycznie
- [x] Dane przetrwają „restart” (test: dwa obiekty repozytorium na jednym pliku)
- [x] Dostęp wielowątkowy (`check_same_thread=False` + lock albo połączenie per wątek) i `journal_mode=WAL`
- [x] `_make_repository()` zwraca SQLite; wszystkie testy przechodzą

## Wskazówki
- `add_reviews` -> `INSERT OR IGNORE` + `changes()` / `rowcount`; `save_predictions` -> `INSERT OR REPLACE`.
- Sortuj w SQL: `ORDER BY created_at DESC, id ASC`; daty zapisuj jako ISO 8601 w UTC, wtedy porównania tekstowe są poprawne.
- `remove_target` usuwa kaskadowo (`ON DELETE CASCADE` + `PRAGMA foreign_keys=ON`) albo w jednej transakcji.

## Poza zakresem
- Pełnotekstowe wyszukiwanie (FTS) – ewentualnie w A3, jeśli będzie potrzebne.

## Notatki z realizacji
**Zrobione 2026-11-04, 7/7.**

- `opimon/storage/db.py`: `connect(path)` tworzy katalog i schemat, ustawia `journal_mode=WAL`,
  `synchronous=NORMAL`, `busy_timeout=30 s`; `check_same_thread=False`. Wersja schematu w
  `PRAGMA user_version` (= 1); baza z nowszym schematem -> czytelny `RuntimeError`.
  Następna zmiana schematu = podbicie `SCHEMA_VERSION` + migracja w `init_schema`.
- Daty jako tekst ISO 8601 w UTC o stałej szerokości (`…T16:39:28.000000+00:00`), więc filtry
  `since`/`until` i `ORDER BY created_at` działają w SQL. Dane w innej strefie są konwertowane do UTC.
- `SqliteReviewRepository`: jedno połączenie na obiekt + `RLock`; każdy zapis to transakcja
  `BEGIN IMMEDIATE` (blokada od razu, bez zakleszczeń z drugim procesem); błąd -> `ROLLBACK`.
- **Bez kluczy obcych**: opinie mogą trafić do bazy przed celem, a predykcje przed opinią (tak jak
  w zaślepce). Kaskada w `remove_target` jest jawna, w jednej transakcji.
- `add_reviews` używa `INSERT … ON CONFLICT(id) DO NOTHING`, a nie `INSERT OR IGNORE`.
  `OR IGNORE` po cichu pomija też wiersze łamiące `NOT NULL` (wykrył to test wycofania transakcji).
- `get_predictions` dzieli listę id na paczki po 500 (limit parametrów SQLite).
- `remove_target` nie ma jeszcze przycisku w GUI (D4).
- Pomiary (laptop, SSD): zapis 20 tys. opinii 0,27 s, analiza 20 tys. zaślepką 0,40 s,
  `scored_reviews` 20 tys. 0,31 s. Na żywo: 300 recenzji Hades II pobranych, po „restarcie”
  (nowe `build_services`) 300 w bazie, 0 do przeanalizowania.
- Testy: kontrakt (wariant `sqlite`) i `tests/test_storage_sqlite.py` (14). Obejmują: trwałość po
  restarcie, schemat, indeksy i WAL, odrzucenie nowszego schematu, tworzenie katalogu, odczyt
  `config.DB_PATH` w chwili wywołania, strefy czasowe, Unicode i JSON w `extra`, 1200 id w
  `get_predictions`, wycofanie transakcji, 8 wątków jednocześnie, zapis z drugiego procesu
  widoczny bez restartu, upsert celu, brak ponownego wczytania próbek po restarcie.
- Skutek dla innych: aplikacja zapisuje dane w `data/opimon.db` (poza repo, `.gitignore`).
  Żeby zacząć od zera, usuń ten plik; przy pustej bazie wczytają się dane przykładowe.
